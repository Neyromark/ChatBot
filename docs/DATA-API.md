# DATA-API 1.0 — документация для проекта CurrentChatBot

Источник: `Data API.pdf` (README репозитория
[stasnorman/example-data-api](https://gitverse.ru/stasnorman/example-data-api), снимок от 30.09.2026).
Пример шаблона дополнительно сверен с `Example/DATA-API.template.yaml` из того же репозитория.

---

## 1. Что такое DATA-API

**DATA-API 1.0** — машиночитаемый формат (YAML) с описанием **обязательных HTTP-проверок** решения,
которое предоставляет собственный API и проходит автоматизированную техническую оценку.

Файл `DATA-API.yaml` — минимальный контракт между решением участника и системой проверки. В нём указывается:

- какие HTTP-запросы выполнить;
- какие параметры передать;
- какие значения сохранить между шагами (`extract`);
- какие есть зависимости между проверками (`dependsOn`);
- какие временные данные удалить после сценария (`cleanup`).

Версия схемы фиксирована: `schemaVersion: "1.0"` (строка, точное совпадение).

### Состав комплекта

| Файл | Назначение |
|---|---|
| `DATA-API.template.yaml` | Официальный шаблон для заполнения |
| `DATA-API.example.yaml` | Заполненный корректный пример |
| `DATA-API.schema.json` | Формальная схема (JSON Schema Draft 2020-12) |
| `validate_data_api.py` | Эталонный валидатор |
| `openapi.yaml` | Минимальный пример OpenAPI 3.1 для локальной проверки |
| `requirements.txt` | Зависимости валидатора |

## 2. Структура файла

```yaml
# DATA-API 1.0
# Не размещайте в этом файле пароли, токены, API-ключи и другие секреты.

schemaVersion: "1.0"

solution:
  name: "<название решения>"
  teamId: "<идентификатор команды>"

api:
  baseUrl: "https://api.example.org"   # только HTTPS
  openapi: "./openapi.yaml"            # необязательно; CLI-параметр --openapi приоритетнее
  defaultHeaders:
    Accept: "application/json"

checks:                                 # только обязательные проверки основной функциональности
  - id: "health"
    name: "API availability"
    description: "Базовая проверка доступности"
    method: "GET"
    path: "/health"                     # относительный путь
    role: "public"                      # public — для endpoint без аутентификации
    expected:
      statusCodes: [200]
      contentType: "application/json"
      requiredFields: ["status"]
    timeoutMs: 5000
    repeatable: true

  - id: "create-item"
    name: "Создание тестового объекта"
    method: "POST"
    path: "/api/items"
    role: "user"
    request:
      headers:
        Content-Type: "application/json"
      body:
        name: "Проверка тестовых данных"
    expected:
      statusCodes: [200, 201]
      contentType: "application/json"
      requiredFields: ["id", "name"]
    timeoutMs: 5000
    repeatable: false
    extract:
      itemId: "$.id"                    # выражение обязано начинаться с $

  - id: "get-item"
    name: "Чтение созданных данных"
    method: "GET"
    path: "/api/items/{itemId}"
    role: "user"
    dependsOn: ["create-item"]
    request:
      path:
        itemId: "${itemId}"             # каждый {param} из path должен быть здесь
    expected:
      statusCodes: [200]
      contentType: "application/json"
      requiredFields: ["id", "name"]
    timeoutMs: 5000
    repeatable: true

cleanup:                                # удаление созданных сценарием данных
  - id: "delete-item"
    method: "DELETE"
    path: "/api/items/{itemId}"
    role: "user"
    request:
      path:
        itemId: "${itemId}"
    expected:
      statusCodes: [200, 204, 404]
    timeoutMs: 5000
```

### Поля проверки (`checks[]`)

| Поле | Обязательно | Описание |
|---|---|---|
| `id` | да | Уникальный идентификатор (повторы — ошибка) |
| `name` | да | Название проверки |
| `method` | да | HTTP-метод |
| `path` | да | Относительный путь, может содержать `{param}` |
| `role` | да | Роль, от имени которой выполняется запрос; `public` — без аутентификации |
| `expected.statusCodes` | да | Допустимые HTTP-коды ответа |
| `expected.contentType` | нет | Ожидаемый `Content-Type` |
| `expected.requiredFields` | нет | Поля, обязательные в JSON-ответе |
| `description` | нет | Пояснение |
| `request.headers` / `request.body` / `request.path` | нет | Заголовки, тело, значения path-параметров |
| `dependsOn` | нет | Список `id` проверок, которые должны выполниться раньше |
| `extract` | нет | Сохранение значений из JSON-ответа: `имя: "$.путь"` |
| `timeoutMs` | нет | Таймаут в миллисекундах, рекомендуемое значение — 5000 |
| `repeatable` | рекомендуется | Можно ли повторять без разрушительных побочных эффектов. Для POST/PUT/PATCH/DELETE без этого поля — предупреждение |

Обязательность полей приведена по README. Точный набор задаёт `DATA-API.schema.json`;
схема не входит в PDF, и при оформлении её стоит сверить.

## 3. Основные правила

1. `schemaVersion` строго равен `"1.0"`.
2. `api.baseUrl` использует **HTTPS**.
3. В `checks` — только обязательные проверки основной функциональности.
4. Каждая проверка содержит `id`, название, метод, относительный путь, роль и ожидаемые коды.
5. Endpoint без аутентификации — роль `public`.
6. Учётные данные тестовых пользователей передаются через защищённый канал проекта оценки и **не хранятся** в `DATA-API.yaml`.
7. Поддерживается OpenAPI 3.0.x и 3.1.x.
8. `timeoutMs` — в миллисекундах, по умолчанию рекомендуется 5000.
9. `repeatable` явно указывает, безопасно ли повторять проверку.
10. Значения из JSON-ответов сохраняются через `extract` и подставляются как `${variableName}`.
11. Созданные сценарием объекты удаляются через `cleanup`.

### Безопасность

В файл **нельзя** помещать: реальные пароли, access/refresh token, API key, приватные ключи,
production credentials, персональные данные тестовых пользователей.
Валидатор предупреждает о буквальном значении заголовка `Authorization`.

## 4. Валидация

Валидатор работает в три этапа:

1. **Структура.** Соответствие `DATA-API.schema.json`.
2. **Семантика.** Взаимосвязи элементов:
   - повторяющиеся `id` в `checks`;
   - ссылки `dependsOn` на несуществующие проверки и зависимость проверки от самой себя;
   - соответствие `{param}` в URL и `request.path`. Отсутствующее значение — **ошибка**, лишний параметр — **предупреждение**;
   - использование `${variableName}` до того, как переменная извлечена через `extract`;
   - выражения `extract` не начинаются с `$`;
   - нет `repeatable` у POST/PUT/PATCH/DELETE (предупреждение);
   - буквальный `Authorization` (предупреждение);
   - path-параметры в `cleanup`.
3. **OpenAPI** (если указан). Проверяются существование файла, его загрузка, версия 3.0.x/3.1.x,
   наличие каждого пути и метода из `checks` и `cleanup`.
   Несовпадение для `checks` — **ошибка**, для `cleanup` — **предупреждение**.

### Запуск

```bash
python -m pip install -r requirements.txt
python validate_data_api.py DATA-API.yaml
python validate_data_api.py DATA-API.yaml --openapi ./openapi.yaml
python validate_data_api.py DATA-API.yaml --schema ./DATA-API.schema.json --openapi ./openapi.yaml
```

### Коды завершения

| Код | Значение | Вывод |
|---|---|---|
| 0 | Файл прошёл проверку (предупреждения допустимы) | `ПОДТВЕРЖДЕНИЕ`, затем блок `ВНИМАНИЕ` при наличии предупреждений |
| 1 | Файл прочитан, найдены ошибки конфигурации | `НЕДЕЙСТВИТЕЛЬНЫЙ` и список нарушений |
| 2 | Проверка не выполнена: нет файла, ошибка чтения, нет схемы и т. п. | — |

Коды позволяют встроить валидатор в CI/CD и shell-скрипты.

### Порядок работы участника

1. Скопировать `DATA-API.template.yaml`.
2. Заполнить сведения об API.
3. Описать обязательные `checks`.
4. Добавить зависимости и `extract`.
5. Добавить `cleanup`.
6. Проверить OpenAPI.
7. Запустить `validate_data_api.py`. Если есть ошибки, исправить и повторить запуск. Если ошибок нет, передать на оценку.

### Совместимость

Совместимые изменения входят в линию 1.x только после официальной публикации новой схемы.
Изменения, которые ломают контракт, обязательные поля или семантику проверок, требуют новой мажорной версии.

## 5. Применимость к CurrentChatBot

**В этом репозитории HTTP API нет.** Поэтому `DATA-API.yaml` для него заполнить нельзя.

- Бот работает через long polling MAX (`dp.start_polling` в `main.py`). Входящих HTTP-запросов он не принимает.
- Связь с мини-приложением идёт через WebSocket, где бот выступает **клиентом**
  (`mailing/miniapp_link.py`, подключение к `settings.MINIAPP_WS_URL`, то есть к сервису CurrentMiniAppBackend).
- Серверных маршрутов (`aiohttp.web`, FastAPI и т. п.) и `openapi.yaml` в проекте нет.

Если решение оценивается по DATA-API, контракт нужно составлять для того сервиса, который
**предоставляет HTTP API**. По архитектуре это CurrentMiniAppBackend. От бота нужно только,
чтобы backend и бот работали с общей БД `MaxBotDispecherTasks`.

### Что потребуется сделать (по месту, где есть HTTP API)

| # | Изменение | Зачем |
|---|---|---|
| 1 | Endpoint доступности, например `GET /health` → `200 {"status": "ok"}`, роль `public` | Базовая проверка из шаблона |
| 2 | Опубликованный `openapi.yaml` (3.0.x/3.1.x), покрывающий все пути из `checks` и `cleanup` | Иначе этап 3 даёт ошибки |
| 3 | HTTPS-адрес для `api.baseUrl` | Правило 2 |
| 4 | Проверки основной функциональности. Исходя из модели данных бота: создание задачи → чтение экземпляра → взятие из пула → завершение; `extract` для `taskId`/`instanceId` | Правила 3, 4, 10 |
| 5 | Endpoint удаления тестовых данных (задач и экземпляров) для `cleanup` | Правило 11. Сейчас удалять задачи можно только вместе с организацией (`delete_organization`) |
| 6 | Явный `repeatable` у всех изменяющих запросов | Без него — предупреждения валидатора |
| 7 | Тестовые учётные данные передаются вне репозитория | Правило 6. Токен бота уже вынесен в `.env` |
